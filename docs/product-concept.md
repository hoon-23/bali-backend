# 제품 컨셉 — 클라이언트(bali-frontend) UI/UX 설계용 브리프

백엔드(`bali-backend`) 설계 문서(`NOTES.md`, `docs/specs/*`, `PROGRESS.md`)에서 추출한 제품 컨셉
정리. `bali-frontend`는 아직 코드가 없는 상태(메모리 폴더만 존재)라, 클라이언트 UI/UX 작업을
시작할 때 참고할 배경 자료로 작성했다. 백엔드 구현이 끝난 도메인/기능은 확정 정보지만,
**UI/UX 방향성(톤·무드·비주얼 스타일)은 아직 아무것도 정해지지 않았다** — 이 문서에도 없다.

## 1. 배경/동기

3년간 애플 기본 메모 앱에 개인적으로 기록해온 운동 기록을 정형화해서, 통계 기반으로 분석해
주간 인사이트를 제공하려는 목적에서 시작된 프로젝트다. 이직 준비 중 도메인 미스매치로 계속
탈락하면서, 포트폴리오로 도메인 무관한 기술력을 증명하려는 동기가 있다(Kronos 일정관리 API에
이은 두 번째 사이드 프로젝트, 배치 처리 아키텍처 판단력을 보여주는 게 목표).

당초 1인용 개인 프로젝트로 러프하게 기획됐다가, 브레인스토밍을 거쳐 멀티유저 지원 구조로 범위가
확장됐다. 지금은 인터뷰용 포트폴리오가 1차 목적이지만, TestFlight 제출을 전제로 설계가 진행 중
이라 — 즉 **실제로 배포 가능한 모바일 앱(사실상 iOS 우선/온리)** 을 만드는 방향으로 가고 있다.

## 2. 핵심 컨셉

사용자가 운동 기록을 **템플릿 기반으로 계획하고 → 실제 수행값을 세션으로 기록하면 → 매주
자동으로 통계가 집계되고 규칙 기반(if/else) 인사이트 문장이 생성되는** 앱.

(원래 스펙 초안에는 이 인사이트를 Claude API/LLM으로 생성하는 안이 있었으나, 2026-08-07에
"일단 통계만으로 충분하다"는 판단으로 폐기했다 — 지금은 순수 통계 집계 + 규칙 기반 문장이다.
LLM 관련 기능은 이 프로젝트 로드맵에서 완전히 제외됐다.)

## 3. 핵심 도메인 개념 (UI가 표현해야 할 것들)

- **User**: 소셜 로그인 4종(Google/Naver/Kakao/Apple), 탈퇴는 소프트 삭제.
- **Exercise(종목)**: GLOBAL 시드(3년치 개인 기록에서 뽑은 기본 종목 59개, variant 조합까지
  치면 더 많음) + PERSONAL(사용자가 직접 등록한 개인 종목). `MuscleGroup`(BACK/CHEST/
  SHOULDER/BICEPS/TRICEPS/LEGS/ABS/CARDIO)으로 분류되고, `type`(STRENGTH|CARDIO)에 따라
  이후 입력 필드가 갈린다(STRENGTH는 세트/반복/무게, CARDIO는 지속시간/페이스).
  - **유사 종목 제안**: 종목 입력 시 실시간으로 유사한 기존 종목을 상위 10개까지 제안한다
    (trigram 유사도, threshold 0.2). 실제 과거 기록에 "바벨로우/바벨로/바벨로우유" 같은 오타성
    변형이 많아서 생긴 기능 — 자동완성/검색 UI 설계 시 참고할 것.
  - 관리자가 사후에 종목을 정규화하는 기능은 **의도적으로 없다**(신뢰도 문제로 배제) — 정규화는
    입력 시점에 사용자 스스로 유사 종목 제안을 보고 판단하는 것으로만 이뤄진다.
- **WorkoutTemplate(운동 템플릿)**: PUSH/PULL/LEGS/STRENGTH 카테고리로 분류되는 재사용 가능한
  루틴 계획. 종목별로 목표값(세트/반복/무게/지속시간/페이스)을 갖는다.
- **WorkoutSession(세션 기록)**: 특정 날짜의 실제 운동 기록. 템플릿에서 복사해서 시작하지만,
  생성 후에는 독립적으로 종목을 자유롭게 추가/변경/삭제할 수 있다. **템플릿에 없던 종목을 그
  자리에서 즉흥적으로 추가하는 경우, 목표값(target) 없이도 기록 가능** — 실제 헬스장에서
  "그때 비어있는 기구로 즉흥적으로 하는" 상황을 반영한 설계다. "세트 기록" 화면을 만들 때
  이 케이스(계획 없이 하는 운동)를 자연스럽게 다뤄야 한다.
- **WeeklyAnalysis(주간 분석)**: 지난 7일 집계(총 운동시간, 종목별/근육군별 볼륨, 유산소
  총시간, 완료율, 전주 대비 증감률) + 규칙 기반 인사이트 문장. 상태값은 SUCCESS/FAILED/
  NO_ACTIVITY.

## 4. 핵심 사용자 플로우 (러프)

1. **로그인**: 소셜 로그인(Google/Naver/Kakao/Apple) → 자체 JWT 발급
2. **종목 조회/등록**: 글로벌 카탈로그 조회 → 유사 종목 제안 활용 → 필요하면 개인 종목 등록
3. **템플릿 만들기**: 카테고리 선택 → 종목/목표값 지정 → 저장
4. **세션 기록**: 날짜 선택 → 템플릿에서 시작(또는 빈 세션으로 시작) → 실제 수행 종목 자유롭게
   추가/변경/삭제 → 실제 수행값 입력 및 완료 체크
5. **주간 리포트 확인**: 집계 지표 + 인사이트 문장 조회

## 5. 현재 구현된 기능 범위

**Phase 1 (완료)**: 소셜 로그인+JWT, 종목 카탈로그(글로벌+개인+유사종목제안), 운동 템플릿
CRUD, 템플릿 기반 세션 기록, 주간 배치 분석(Airflow가 매주 월요일 트리거), 주간 리포트 조회.

**Phase 2 (진행 중, #1~#4 완료)**: Swagger/OpenAPI 문서화, 세션 삭제, 개인 종목 수정/삭제,
소셜 로그인 확장(네이버/카카오/애플 추가 — 최초엔 Google만 있었음).

**Phase 2 남은 후보(미착수, 순서 미확정)**: 세트 타이머(세트별 시작/종료 기록 — 클라이언트
UI에 직접 영향), PR(개인 기록) 감지, 통계 대시보드, 템플릿 공유(다른 유저 템플릿 fork/copy),
자연어 질의 API(**로드맵 제외가 아니라 "보류" 상태** — Claude API 배제 결정과 충돌해서 비-LLM
형태로 재검토가 필요한 상태로 남아있음, 완전히 죽은 아이디어는 아님).

## 6. 명시적으로 범위 밖인 것

- 관리자에 의한 사후 종목 정규화 — 의도적으로 없음 (위 3번 참고)
- 3년치 개인 기록 마이그레이션 — 정식 기능이 아니라 본인 계정 시딩용 1회성 스크립트일 뿐
- Claude API/LLM 기반 자연어 인사이트 — 로드맵에서 완전히 제외 (단, 자연어 "질의" API 자체는
  위 5번처럼 비-LLM 형태로는 여전히 후보로 남아있음 — 인사이트 "생성"과 질의 "응답"은 다른
  얘기라는 점에 유의)

## 7. 타겟 사용자 / 플랫폼 전제

- 1차: 작성자 본인(3년치 개인 운동 기록 기반) + 이직 포트폴리오로서 면접관에게 어필
- 완성도에 따라 실제 서비스로 확장할 가능성은 열려있으나, **구체적인 타겟 유저 페르소나는
  아직 정의된 바 없음** — 뭘 가정하지 말고 필요하면 이 단계에서 새로 정의해야 함
- **TestFlight 제출을 전제로 설계 진행 중 → 사실상 iOS 우선/온리 앱**. Android 대응 여부는
  불확정. 디자인 시스템을 고를 때 iOS HIG를 기본으로 고려하는 게 합리적으로 보임(단, 확정된
  결정은 아님).

## 8. 톤 / 무드 / 비주얼 방향성

**아무것도 정해진 게 없다.** 지금까지 나온 모든 문서가 백엔드 설계 문서라서, 브랜드 톤이나
비주얼 스타일, 디자인 시스템에 대한 언급이 전혀 없다. 이 부분은 클라이언트 UI/UX 작업을 시작할
때 처음부터 정의해야 하는 영역이다.

## 9. TestFlight 전 처리 필요 (UI에도 영향, 별도 트랙)

로그인 기능이 있어 개인정보보호법(PIPA) 관점에서 실제 갭이 파악돼 있다 — 아직 구현은 안 됨:
- 탈퇴가 소프트 삭제뿐이라 실제 파기 로직이 없음
- 개인정보처리방침이 아예 없음
- 소셜 로그인(특히 Google, Apple — 해외 기업)으로 인한 국외 이전 고지 누락
- (2026-08-11 확인) 네이버는 access token이 실제 우리 앱에 발급된 게 맞는지 검증하는 API가
  없어서, 서버 쪽에 알려진 보안 리스크가 남아있음 — TestFlight 전 재설계 필요

이건 백엔드/정책 트랙 작업이지만, **UI에도 직접 영향**을 준다 — 로그인 동의 화면, 개인정보
처리방침 열람 화면, 탈퇴 시 안내 문구("파기"가 아니라 "비활성화"에 가깝다는 걸 사용자에게
어떻게 정직하게 전달할지) 등은 클라이언트 화면 설계 범위에 들어간다.
