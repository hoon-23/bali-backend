# 주간/월간 분석 지표 재설계: 빈도와 강도 분리

2026-10-02. bali-backend 변경. 계기: 인사이트 "이번 달 볼륨이 지난달보다 331.1% 증가했어요"처럼 증가율이 수백 %로 나와 사용자가 실제보다 크게 오해한다(bali-frontend 세션이 사용자 지적이라고 전달, 사용자와 직접 브레인스토밍해 방향 확정).

## 문제
지금 증감 인사이트는 볼륨 **총합**과 맨몸 반복수 **총합**을 직전 기간과 비교한다. 총합은 운동 횟수에 비례하므로 "더 세게 했다"와 "더 자주 갔다"가 한 숫자에 섞이고, 직전 기간에 운동이 적었으면 분모가 작아져 증가율이 튄다.
로컬 실제 계정의 월별 데이터: 완료 로그 6개(볼륨 9,975) → 14개(18,025)로 +81%, 9개(13,210) → 31개(33,864)로 +156%. 볼륨이 로그 수와 같이 움직인다.

## 결정 사항
- 지표를 **빈도**(얼마나 자주)와 **강도**(한 번에 얼마나)로 나눈다.
- 강도는 **세션당 평균**으로 비교하고 퍼센트 표기를 유지한다. 빈도는 퍼센트 없이 **횟수**로 표기한다.
- 문장 인사이트 방식은 유지한다(프론트 변경 최소). 요약에 저장하는 값은 나중에 구조화 지표(카드/그래프)로 확장할 때 그대로 쓸 수 있게 한다.
- 이미 저장된 과거 요약/인사이트는 그대로 둔다(백필 안 함). 세션 수가 없는 구버전 요약이 직전 기간이면 증감 문장을 생략한다.
- 대칭 변화율처럼 상한만 막는 공식은 숫자의 의미가 틀어져 채택하지 않는다.

## 지표 정의
- **운동 세션**: 완료된 로그(`completed=true`)가 1개 이상인 세션. 상태는 보지 않는다(자정에 ABANDONED로 바뀐 세션도 실제로 운동했으면 센다. 볼륨 집계와 같은 기준이다). 응답의 `completedSessionsCount`(status COMPLETED 개수)와는 다른 값이다.
- **빈도** = 기간 내 운동 세션 수.
- **세션당 볼륨** = 총 볼륨 ÷ 볼륨이 0보다 큰 세션 수(무게가 기록된 근력 로그가 있는 세션). 유산소나 맨몸만 한 세션은 분모에서 뺀다.
- **세션당 맨몸 반복수** = 맨몸 총 반복수 ÷ 맨몸 반복수가 0보다 큰 세션 수.

## 인사이트 규칙
순서: 빈도 → 세션당 볼륨 → 완료율 → 근육군 비중 → 세션당 맨몸 반복수. 주간은 "이번 주/지난주", 월간은 "이번 달/지난달"로 쓴다.

### 빈도
직전 기간 횟수를 알 때만 만든다(직전 분석이 없거나 FAILED이거나 구버전 요약이면 생략). 직전 분석이 NO_ACTIVITY면 0회로 본다.

| 상황 | 문장 |
|---|---|
| 횟수가 다름 | "지난주 3회 → 이번 주 4회" (직전 0회 포함: "지난주 0회 → 이번 주 3회") |
| 횟수가 같고 최소 횟수 이상 | "이번 주도 3회, 꾸준해요" |
| 횟수가 같고 최소 횟수 미만 | 없음 |

최소 횟수: 주간 2회, 월간 4회. 월간 예: "지난달 9회 → 이번 달 12회", "이번 달도 12회, 꾸준해요".

### 강도 (세션당 볼륨, 세션당 맨몸 반복수)
증감률 = (이번 세션당 평균 − 직전 세션당 평균) ÷ 직전 세션당 평균 × 100, 소수 1자리.
아래 중 하나면 증감률은 null이고 문장도 없다: 직전 요약이 없음, 직전 요약에 해당 세션 수가 없음(구버전), **직전 해당 세션이 2회 미만**, 이번 기간 해당 세션이 0회.

| 증감률 | 문장 |
|---|---|
| +10% 이상 ~ +100% 이하 | "이번 주 세션당 볼륨이 지난주보다 25.0% 증가했어요" |
| +100% 초과 | "이번 주 세션당 볼륨이 지난주보다 크게 늘었어요" |
| −10% 이하 | "이번 주 세션당 볼륨이 지난주보다 15.0% 감소했어요" |
| 그 사이 | 없음 |

맨몸은 "세션당 볼륨" 자리에 "세션당 맨몸 운동 반복수"를 쓴다. 100% 초과 정성 표현은 세션당 평균으로도 드물게 튀는 경우의 안전망이다.

### 그대로 두는 규칙
완료율 70% 미만("완료율이 60.0%로 낮은 편이에요"), 근육군 세트 비중 15% 미만은 원래 비율 값이라 변경 없다.

## 데이터 (스키마 변경 없음)
`AnalysisSummary`에 필드를 추가한다. 요약은 JSONB 문자열이라 구버전 행은 기본값(null)으로 읽힌다.
- `sessionCount: Int?` 운동 세션 수
- `previousSessionCount: Int?` 직전 기간 운동 세션 수(모르면 null)
- `weightedSessionCount: Int?` 볼륨이 있는 세션 수
- `bodyweightSessionCount: Int?` 맨몸 반복수가 있는 세션 수

`volumeChangeFromLastWeekPercent`, `bodyweightRepsChangeFromLastWeekPercent`는 **이름은 그대로, 의미가 총량 증감에서 세션당 평균 증감으로 바뀐다.** 새 필드 네 개는 `AnalysisSummaryResponse`에도 그대로(nullable) 내려준다.

## 구현
- core: 주간/월간 계산기가 거의 같은 코드라 공용 `PeriodStatsCalculator`(가칭)로 계산과 문장 생성을 모으고, `WeeklyStatsCalculator`/`MonthlyStatsCalculator`는 기간 라벨과 최소 횟수만 넘기는 얇은 진입점으로 남긴다.
- 계산기 입력을 `logs`에서 `sessions: List<WorkoutSession>`로 바꾼다(세션 단위 집계에 필요, 중단 로그 id도 세션에서 얻는다). 직전 기간은 `previousSummary`와 `previousSessionCount`를 받는다.
- batch: 주간/월간 러너가 직전 분석을 조회해 `previousSessionCount`를 정한다(없음/FAILED → null, NO_ACTIVITY → 0, SUCCESS → `summary.sessionCount`).
- api: 이번 주/이번 달 실시간 집계(`/current`)도 같은 계산기를 쓰므로 호출부를 맞춘다. 응답 DTO에 새 필드 추가.
- 푸시 요약 러너는 인사이트 문장을 쓰지 않아 영향 없다.

## 프론트 영향 (bali-frontend에 전달)
- 인사이트 문장은 서버 문자열을 그대로 보여주므로 변경 없음. 과거 인사이트는 옛 문구로 남는다.
- 프론트가 `bodyweightRepsChangeFromLastWeekPercent`로 직접 만드는 문구("지난 주보다 N% 증가")는 "세션당" 의미로 바꿔야 한다. `volumeChangeFromLastWeekPercent`를 직접 쓰는 곳이 있으면 같다.
- 증감률이 null로 오는 경우가 늘어난다(직전 세션 2회 미만, 구버전 요약).

## 테스트
- 계산기: 세션당 평균(같은 강도로 횟수만 늘면 증감 0%), 분모에서 유산소/맨몸 전용 세션 제외, 직전 2회 미만/구버전이면 null, 100% 경계(정확히 100.0은 퍼센트, 초과는 "크게 늘었어요"), 빈도 문장(다름/같음+최소 이상/같음+미만/직전 0회/직전 모름), 문장 순서, 주간·월간 라벨.
- 러너: 직전 분석 상태별 `previousSessionCount`, 구버전 요약 다음 기간에 증감 문장이 없는지.
- 컨트롤러: `/current`와 조회 응답에 새 필드가 내려오는지.
- 로컬에서 앱/배치를 실제로 실행해 확인한 뒤 push한다(XP 인정 조건 커밋 `800b15b`와 한 번에).
