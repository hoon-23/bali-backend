# ADR-0006: 소셜 로그인은 클라이언트가 받은 토큰을 서버가 검증

- 상태: 채택됨
- 결정일: 2026-08-11
- 소급 작성: 2026-11-24

## 맥락

앱이 Google, Apple, Kakao, Naver 로그인을 지원해야 한다. 처음 설계는 Google만 서버에서 OAuth로 처리하는 구조였다.
모바일 앱에서는 각 provider의 SDK가 로그인 화면을 띄우고 토큰을 앱에 돌려주는 방식이 일반적이다.

## 결정

앱이 SDK로 받은 토큰을 서버에 보내면, 서버가 그 토큰이 해당 provider가 발급한 것이 맞는지 검증하고 자체 JWT를 발급한다.
검증은 두 갈래다.
- Google, Apple, Kakao: OIDC ID Token을 provider의 공개키(JWKS)로 서명 검증하고, 대상(`aud`)이 우리 앱인지까지 확인한다. 키만 캐싱하므로 요청마다 provider를 호출하지 않는다.
- Naver: access token으로 provider의 사용자 정보 API를 호출해 신원을 확인한다.

## 검토한 대안

- 서버 주도 OAuth 리다이렉트(웹 방식): 모바일 앱에 맞지 않고 Apple 심사 기준과도 맞지 않는다고 판단했다.
- Kakao를 access token + 사용자 정보 API로 처리: 최초 설계는 이 방식이었다. 최종 리뷰에서 audience 검증이 빠진 것을 발견했고, Kakao가 OIDC ID Token을 발급한다는 것을 확인해 OIDC 방식으로 바꿨다.
- Naver를 OIDC로 검증: Naver는 ID Token도 토큰 검증 API도 제공하지 않아 대안이 없다.

## 결과

- 얻는 것: 모바일 흐름에 맞고, 세 provider는 서버가 토큰의 발급 대상까지 검증한다.
- 감수하는 것: **Naver는 토큰이 우리 앱에 발급된 것인지 확인할 방법이 없다.** 알려진 보안 위험이며 아직 해결하지 못했다. 다른 앱용으로 발급된 Naver 토큰으로도 우리 서버에 로그인할 수 있다(계정 탈취는 아니고 앱 신원 위장). 해결하려면 서버가 authorization code를 직접 교환하는 방식으로 클라이언트 로그인 흐름을 바꿔야 하며, 설계서는 실제 사용자 데이터가 걸리기 전에 재검토하도록 적어 두었다.
- 부수 결정: 최초 로그인인데 Apple이 이메일을 주지 않으면 가입을 거부하지 않고 임시 이메일로 가입시킨다. 거부하면 그 사용자가 그 계정으로 영구히 가입할 수 없고, 임시 이메일은 나중에 고칠 수 있기 때문이다. 이메일 발송 기능을 만들 때는 임시 도메인을 제외해야 한다.
