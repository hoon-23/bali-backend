# 아키텍처 결정 기록 (ADR)

중요한 기술 결정을 **"왜 그렇게 골랐는가"** 중심으로 한 장씩 남기는 기록입니다.
설계서([`docs/specs`](../specs/README.md))가 "무엇을 어떻게 만들지"를 설명한다면, ADR은 대안과 trade-off를 남깁니다.
현재 구조는 [architecture](../architecture.md)를 보세요.

## 작성 규칙

**쓰는 경우**
- 되돌리기 어렵거나 비용이 큰 결정
- 실제로 대안이 있었고 trade-off가 있었던 결정
- 나중에 "왜 이렇게 했지?"라고 물을 만한 결정

**쓰지 않는 경우**
- 되돌리기 쉬운 구현 세부
- 한 줄이면 설명되는 것

**형식**
- 파일명은 `NNNN-kebab-case.md`입니다. 번호는 **작성 순서**이고 결정일과는 무관합니다.
- 템플릿은 저장소의 `docs/adr/0000-template.md`입니다(사이트에는 게시되지 않음).
- 한 ADR은 한 화면(약 40~60줄) 안에 씁니다. 길어지면 상세는 설계서로 링크합니다.
- 검토한 대안은 실제로 검토한 것만 씁니다. 근거가 없으면 비웁니다.

**상태**
- `제안됨`: 논의 중
- `채택됨`: 결정되어 적용 중
- `대체됨(→ ADR-NNNN)`: 이후 다른 결정으로 바뀜. 옛 문서는 지우지 않습니다.
- `폐기됨`: 결정을 취소함

**바꾸는 방법:** 확정된 ADR은 상태 줄 외에는 고치지 않습니다. 결정이 바뀌면 새 ADR을 쓰고, 옛 ADR의 상태만 `대체됨(→ ADR-NNNN)`으로 바꿉니다.

**소급 작성:** 이미 내린 결정을 나중에 기록한 ADR은 `소급 작성` 날짜를 표시합니다. 결정일은 근거 문서의 날짜입니다.
